# Pinned ChatLoop host reference

`fixtures/host-loop/sdk-chatloop.json` is generated by **Go executing the real SDK
ChatLoop and Runner**, not by Rust, a reimplementation of ChatLoop, or handwritten
expected transcripts. The module imports `github.com/gratefulagents/sdk v0.0.115`
and replaces it with `../../repos/sdk`, exactly the local-checkout approach used
by `scripts/trace-reference`. The authoritative checkout must be clean at:

```
1dc92b73900fac74dc357a938e4b5eee6392b418
```

Source contract inspected: `repos/sdk/pkg/agentsdk/chatloop.go`,
`chatloop_test.go`, `chatloop_multi_approval_test.go`, `conversation.go`, and the
public aliases' underlying Runner/model/items/config/hooks/result definitions.
SDK sources are never edited. There are no network model calls, actual platform
mutations, Rust-produced expectations, worker CLI/evaluation integration, or
migration-ledger changes. This is bounded host-composition evidence, **not a
claim of complete SDK parity or acceptance closure**.

## Files and execution

- `main.go`: spies for every SessionStore, ConfigSource, PlatformToolFactory,
  ApprovalGate, TraceStore, and RunStatusSink method; scripted model and tools;
  real `NewChatLoop(...).Run(...)`; observation serialization.
- `scenarios.go`: executable scenario inputs, emitted in full beside observations.
- `main_test.go`: independent semantic assertions on ordering, pagination,
  preparation, persistence/error short circuits, approval batching, and limits.
- `check.py`: checks clean pin and local module replacement, regenerates twice
  in memory, compares **exact bytes**, and rechecks SDK cleanliness. It never
  rewrites the fixture or SDK.
- `../../fixtures/host-loop/sdk-chatloop.json`: 46 scenario records, 47 Run calls
  (one scenario calls the same loop twice).

From the repository root:

```sh
export GOROOT=/usr/local/go GOTOOLCHAIN=local
export GOPATH=/workspace/scratch/go GOCACHE=/workspace/scratch/go-cache

(cd scripts/host-reference && /usr/local/go/bin/go test -mod=readonly -count=1 ./...)
```

Intentional regeneration (first verify the checkout pin/cleanliness with the

```sh

```

The checker sets the above Go environment explicitly and uses
`/usr/local/go/bin/go` (`go.mod` requires Go 1.26.2; initial generation and
verification used `go1.26.8 linux/amd64`). Runner diagnostic logging goes
to stderr, not into expected data; the checker captures it and shows stderr if
execution fails. No SDK logging configuration is changed.

## Fixture schema and observation boundary

Each case has `name`, `spec`, `runs`, and `original_agent_tools_after`.
Each Run records `cursor_before`, `cursor_after`, ordered `calls`, `result`, and
`error`. Errors retain their exact message and a category: the ChatLoop wrapper
prefix, or `runner` for errors propagated from Runner. A null result is distinct
from a non-null combined result with an error.

`spec` includes initial cursor, limits, permission/config/state/handoff inputs,
ordered session pages, model responses and usage, tool definitions, ordered gate
decisions, and method failure injection. `Fail[method] = n` injects an error on
the nth call across all Runs in that case; the failed call itself is recorded.
Absent map entries do not fail. Pages are served in script order, while every
requested cursor and limit is recorded. Append is a spy, not a history-producing
store; subsequent Runs receive only the scripted page and configured handoff
history. Unscripted page/model/gate consumption panics. Script entries after an
early return can intentionally be unused.

All scenarios attach config/session/factory/trace/status spies. Only the gate
can be absent. Base agent name, model name, and instructions are fixed in
`execute`. Tracing is disabled and PromptCacheNamespace is explicitly fixed to
`host-reference-fixed`; the actual resulting model cache key is recorded.
`runner.start` is the public `OnAgentStart` hook (which can occur more than once
inside one Runner.Run), exposing the prepared config and tool surface.
`model.response` denotes a request delivered through StreamResponse; its helper
GetResponse chooses the scripted response. Buffered streams emit item events,
then Complete, then an Error event when requested. Thus the partial-response
error case actually presents a complete response snapshot before failure.

Result projection includes final output/text, last agent name, NewItems,
FinalHistory, model response items/usage/EndTurn/context tokens, cumulative usage,
interruption fields including parent context, last response ID, and tool-input
and tool-output guardrail results. It does not serialize executable Agent fields,
provider Raw/cost accounting, general agent guardrail results, or action audit
records. These are not covered contracts here. Item/tool projections use the
SDK's public SnapshotRunItems/SnapshotTools to avoid executable callbacks and
recursive Agent objects. Append calls explicitly retain `count`, including zero;
SDK item snapshots represent empty slices as null.

**No regex, global string scrubbing, UUID replacement, or timestamp removal is
performed.** Runtime trace IDs/times are not part of the chosen observation
schema. UserMessage.CreatedAt is a deterministic zero value in the input specs;
user-supplied timestamp/ID-looking strings, whitespace, image metadata/base64,
call IDs, and parent-context payloads are retained. Raw JSON is JSON-encoded in
item snapshots; gate and tool inputs are also recorded as exact strings so their
original whitespace remains observable. Fixed cache namespace avoids an
irrelevant generated namespace rather than normalizing user data. The generated
namespace branch itself is outside this fixture's coverage.

## Exact covered scope

The 46 case names are authoritative and enumerate these bounded contracts:

- Preparation order: permission → directive → guardrail rules → mode snapshot →
  working state → factory → handoff history → session pages → runner/model.
  Each host preparation method's error stops subsequent calls. Bad regex,
  action, and rule type fail compilation before mode/state/model.
- Permission defaults, read-only and unknown-value fail-closed behavior,
  workspace approval, normalized danger-full-access, explicit policy/access
  precedence, read-only snapshot clamp, turn/subagent-limit fill vs override,
  and an actually enforced snapshot MaxTurns limit.
- Additional instructions plus directive; working-state replacement on step or
  summary presence vs retention for goal-only state; factory receives base tools
  without changing the original Agent tool list; handoff precedes fresh input
  and preserves earlier assistant provenance. Working state is captured in
  RunConfig, **not asserted to appear directly in initial model instructions**.
- Default message limit 50 with 51 messages; custom limit pagination, full page
  followed by empty page, blank-message skipping without skipping cursor
  advancement, image-only input, verbatim text, stuck cursor termination,
  token-only cursor advancement, and page failure after a successful advance.
- Repeated Run on the same loop retains cursor but adds no implicit transcript.
  Model errors retain consumed cursor but return nil, discarding partial response
  and previous runner-turn results. A resume error also discards the combined
  result without undoing already-appended batches or executed effects.
- Empty NewItems still causes AppendRunItems. Append fails before any
  finalization; trace finalization precedes status final publication; failures
  return the combined result and prevent later collaborators.
- Two pending approvals: persist runner batch, resolve both, append generated
  approval/output batch, then resume with both paired outputs. Approved execution
  uses compiled tool-input/output guardrails, with accumulated tool guardrail
  results and usage visible in the combined result.
- No gate synthesizes denied approval/output pairs and finalizes without another
  model call. At this pin its result **remains interrupted**, and FinalHistory is
  still the runner's interrupted history rather than the generated denial batch;
  the fixture preserves this distinction instead of repairing it.
- Gate denials trim explicit reasons and default blank reasons. A pause from the
  first approved tool still resolves the second pending tool, persists the whole
  batch, clears interruption fields, adopts resolved history, and finalizes.
- Gate failure after the first approved effect persists that partial generated
  batch before returning the gate error. If that append also fails, append error
  takes precedence. Initial/approval/no-gate-denial append failures have separate
  cases. The real runner's original approval records and generated decision
  records are retained without deduplication.
- MaxResumes=1 and default MaxResumes=0 (effective 12): the next interrupted runner
  batch is appended before the limit error; no gate call or finalization follows.

RoleCatalog, PublishProgress, PublishTraceID, TraceStore.RunDir, AppendCategory,
and WriteFile are implemented as spies but are **not called by ChatLoop in these
cases**. Their absence is visible, not simulated success. Status/trace object
finalization observations are separate from runner tracing, which is disabled.

## Not covered / not claimed

No nil-loop/missing-runner/missing-agent validation fixtures, absent optional
config/session/factory/trace/status permutations, cancellation, real timeouts,
retries/fallback models, warning/log guardrail side effects, concurrent racing
host calls, subagent execution, real MCP or platform tools, specialist catalog
construction, mid-run compaction/FinalHistory rewrite, durable checkpoints,
provider token accounting, or actual trace-store filesystem behavior. Capturing
SubAgentMaxTurns proves preparation only, not child-agent enforcement. Nonzero
negative limit values are not separately exercised. Callback slices sharing
host-owned backing arrays are not probed. Approval restore-parent-context failure
and approved-tool execution errors are not injected; gate failure after partial
effects **is** exercised. Real-time timeout and compaction scenarios would need
separate carefully controlled fixtures, not fabricated expectations.
